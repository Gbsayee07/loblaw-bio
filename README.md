# Loblaw Bio — Immune Cell Population Analysis

Analysis of immune cell population frequencies from `cell-count.csv`, built for
Bob Loblaw's clinical trial review. Loads the data into a SQLite database,
answers Parts 1-4 of the analysis brief, and exposes the results through an
interactive Streamlit dashboard.

## Quick start (GitHub Codespaces)

```bash
make setup       # install dependencies
make pipeline    # build the database and generate all tables/plots
make dashboard   # launch the interactive dashboard
```

`make dashboard` starts Streamlit on port 8501. In Codespaces, use the
"Ports" tab to open the forwarded port in your browser.

**Dashboard link:** https://loblaw-bio-nqzrgrjebkz4juchvzb9rt.streamlit.app/

The deployed app reads from `cell_counts.db`, which is committed to this
repository, so it's live with data immediately (no setup needed to view it).
It can also be run locally or in Codespaces via `make dashboard` as shown
above, which is how it will be started for grading.

## Part 1 — Database schema

The database (`cell_counts.db`, generated by `load_data.py`) uses four
normalized tables:

```
projects(project_id PK)

subjects(subject_id PK, project_id FK, condition, age, sex, treatment, response)

samples(sample_id PK, subject_id FK, sample_type, time_from_treatment_start)

cell_counts(id PK, sample_id FK, population, count)
```

**Why this shape:**

- **One row per subject, not per sample, for condition/treatment/response/sex/age.**
  Checking the source data confirms these fields are constant within a
  subject (each subject has exactly one condition, one treatment, one
  response, etc., across all of their samples). Storing them once on
  `subjects` instead of repeating them on every sample avoids duplication
  and keeps the data consistent — there is only one place to update if a
  subject's response label ever changes.
- **`samples` sits between `subjects` and `cell_counts`** because a subject
  contributes multiple samples over time (`time_from_treatment_start` =
  0, 7, 14 in this dataset) and possibly multiple sample types (PBMC, WB).
  This is a natural one-to-many relationship.
- **`cell_counts` is stored long (one row per sample-population pair),
  not wide (one column per population).** This is the most important
  design choice for scalability: adding a new cell population (say, a
  6th marker the lab starts measuring) requires zero schema changes —
  it's just new rows, not a new column and a migration. It also makes
  the population-level queries used throughout this project (frequency
  calculations, group-by-population stats) simple joins/group-bys
  instead of repeated per-column logic.

**Scaling to hundreds of projects, thousands of samples, and more analytics:**

- The schema already scales structurally: `projects` → `subjects` →
  `samples` → `cell_counts` is a standard star-like layout, and none of
  the relationships change as data volume grows. Indexes on the foreign
  keys (`subjects.project_id`, `samples.subject_id`, `cell_counts.sample_id`,
  `cell_counts.population`) keep the common filters (by project, by
  subject, by population) fast as row counts increase.
- For production scale, SQLite itself is the main thing that would change
  — the same schema maps directly onto Postgres/MySQL, gaining
  concurrent writes and better performance at high row counts. No
  redesign needed, just a different engine.
- The long `cell_counts` format means new analytics (new populations,
  new panels, new assays) are additive, not disruptive. A new assay
  type could be added either as new `population` values, or, if it
  needs its own metadata (units, instrument, panel version), as a
  sibling table (`assays`) referenced from `cell_counts` — this keeps
  `cell_counts` itself lightweight and avoids sparse wide tables.
- If sample metadata grows richer (e.g. additional clinical variables,
  multiple treatments per subject over time, dosing schedules), those
  are naturally handled by adding new tables that reference `subjects`
  or `samples` by their existing primary keys, rather than widening the
  existing tables.

## Part 2 — Sample overview

`src/part2_frequencies.py` computes, for every sample, the total cell
count (sum across all five populations) and each population's count and
percentage of that total. Output:
`outputs/cell_frequencies.csv` with columns `sample, total_count,
population, count, percentage`.

## Part 3 — Statistical analysis

`src/part3_stats.py` restricts to melanoma, miraclib-treated, PBMC
samples, and compares relative frequencies between responders (`response
= yes`) and non-responders (`response = no`) for each of the five
populations.

Two tests are reported side by side, since they make different
assumptions:

- **Mann-Whitney U** — non-parametric, makes no assumption about the
  shape of the underlying distribution. Used as the primary test since
  cell frequency data doesn't reliably meet normality assumptions.
- **Welch's t-test** — parametric, does not assume equal variances
  between groups, reported alongside Mann-Whitney for a familiar,
  standard comparison and as a robustness check.

A population is flagged as significant if either test gives p < 0.05.
Outputs:

- `outputs/responder_vs_nonresponder_stats.csv` — per-population
  results table
- `outputs/boxplots/*.png` — one boxplot per population, plus a
  combined `all_populations.png`

At the time of writing, **cd4_t_cell** is the only population with a
statistically significant difference between responders and
non-responders under both tests (responders show a higher relative
frequency). No other population reaches p < 0.05 under either test —
see `outputs/responder_vs_nonresponder_stats.csv` for exact values, as
these will regenerate from the data on each pipeline run.

## Part 4 — Baseline subset analysis

`src/part4_subset.py` filters to melanoma, PBMC, miraclib-treated
samples at baseline (`time_from_treatment_start = 0`) and reports:

- samples per project (`outputs/part4_samples_per_project.csv`)
- responders vs non-responders, by subject (`outputs/part4_response_counts.csv`)
- male vs female, by subject (`outputs/part4_sex_counts.csv`)

The full filtered subset is written to
`outputs/part4_baseline_subset.csv`.

## Dashboard

`dashboard/app.py` is a Streamlit app with three tabs:

1. **Sample Overview** — filterable table and chart of per-sample
   relative frequencies (Part 2), filterable by condition, treatment,
   sample type, and sex.
2. **Responder vs Non-Responder** — the Part 3 statistical comparison
   table, significance summary, and an interactive boxplot per
   population.
3. **Baseline Subset** — the Part 4 breakdown (samples per project,
   responders/non-responders, sex), plus an ad-hoc explorer for
   averaging absolute cell counts over any condition / sex / response /
   timepoint / population combination.

Run locally with `make dashboard` (or `streamlit run dashboard/app.py`).

## Code structure rationale

- **`load_data.py` is standalone in the repo root** (per the submission
  requirement) and only handles schema creation + CSV loading — no
  analysis logic, so it stays simple and is easy to verify in isolation.
- **Parts 2-4 are separate modules under `src/`**, each independently
  runnable (`python -m src.part2_frequencies`, etc.) and each exposing a
  `main()` plus reusable functions (e.g. `compute_frequencies`,
  `get_filtered_frequencies`, `run_stats`). The dashboard imports these
  same functions directly rather than re-implementing the logic, so the
  numbers in the dashboard and the numbers in `outputs/*.csv` are
  guaranteed to match.
- **`pipeline.py` orchestrates all four parts in order**, giving a
  single command (`make pipeline`) that reproduces every output file
  from scratch.
- **All generated artifacts go to `outputs/`**, keeping generated files
  separate from source code.
